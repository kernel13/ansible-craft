# Phase 5: Playbook Generation - Research

**Researched:** 2026-01-19
**Domain:** Ansible playbook structure, project organization, inventory patterns, group_vars, multi-play orchestration
**Confidence:** HIGH

## Summary

Phase 5 builds directly on Phase 4's established patterns. The existing two-phase generation architecture (plan then generate), file marker parsing, YAML validation, and FQCN/idempotency checking can be reused with minimal adaptation. The key differences are:

1. **Output structure** - Playbook projects generate multiple files (playbook.yml, group_vars/, inventory.example, README.md) vs role directory structure
2. **YAML structure** - Playbooks use plays with hosts/tasks/handlers vs roles with tasks/defaults/vars
3. **Plan schema** - Different fields: plays with host groups vs tasks with modules
4. **Prompt templates** - Playbook-specific guidance for multi-play orchestration, group_vars organization, inventory patterns

**Primary recommendation:** Create a parallel `generation/playbook/` module mirroring `generation/role/` but with playbook-specific structure.ts, prompts, and plan schema. Reuse parser.ts, validation/, and writer.ts infrastructure directly.

## Playbook Project Structure

Per CONTEXT.md decisions, generated playbook projects follow this structure:

```
playbook-name/
├── playbook.yml          # Main playbook with one or more plays
├── inventory.example     # Example INI inventory file
├── group_vars/
│   ├── all.yml           # Variables for all hosts
│   ├── webservers.yml    # Variables for webservers group
│   └── databases.yml     # Variables for databases group (if applicable)
└── README.md             # Usage instructions with ansible-playbook examples
```

### Playbook.yml Structure

A well-organized playbook contains:

```yaml
---
# Deploy LAMP Stack
# Generated by ansible-craft

# Pre-flight validation
- name: Validate deployment prerequisites
  hosts: all
  gather_facts: true
  pre_tasks:
    - name: Validate required variables
      ansible.builtin.assert:
        that:
          - app_name is defined
          - db_password is defined
        fail_msg: "Required variables not set"

# Web server deployment
- name: Configure web servers
  hosts: webservers
  become: true

  pre_tasks:
    - name: Gather package facts
      ansible.builtin.package_facts:
        manager: auto

  tasks:
    - name: Install Apache packages
      ansible.builtin.apt:
        name: "{{ apache_packages }}"
        state: present
        update_cache: true
        cache_valid_time: 3600
      # Could be extracted to role: webserver

    - name: Deploy Apache configuration
      ansible.builtin.template:
        src: apache.conf.j2
        dest: /etc/apache2/sites-available/app.conf
        mode: '0644'
      notify: Reload Apache

  handlers:
    - name: Reload Apache
      ansible.builtin.service:
        name: apache2
        state: reloaded

  post_tasks:
    - name: Verify Apache is responding
      ansible.builtin.uri:
        url: "http://localhost:{{ apache_port }}/"
        status_code: 200
      retries: 3
      delay: 5

# Database deployment
- name: Configure database servers
  hosts: databases
  become: true
  # serial: 1  # Uncomment for rolling updates to avoid all DBs down at once

  tasks:
    - name: Install MySQL packages
      ansible.builtin.apt:
        name: "{{ mysql_packages }}"
        state: present

  handlers:
    - name: Restart MySQL
      ansible.builtin.service:
        name: mysql
        state: restarted
```

```typescript
### Play Organization

1. **Multiple plays** - Separate plays for different host groups
2. **Play execution order**:
   - pre_tasks (validation, fact gathering)
   - tasks (main work)
   - handlers (triggered by notify)
   - post_tasks (verification)

3. **pre_tasks usage** - Use for:
   - Variable validation with assert/fail
   - Gathering additional facts
   - Prerequisite checks

4. **post_tasks usage** - Use for:
   - Service health verification
   - Smoke tests
   - Notification of completion

5. **Handlers** - Define per-play, not global:
\`\`\`yaml
- name: Configure webservers
  hosts: webservers
  tasks:
    - name: Deploy config
      ansible.builtin.template:
        src: app.conf.j2
        dest: /etc/app/app.conf
      notify: Restart app

  handlers:
    - name: Restart app
      ansible.builtin.service:
        name: app
        state: restarted
\`\`\`
```

## Playbook Project Structure Module

```typescript
// src/generation/playbook/structure.ts

export const PLAYBOOK_DIRECTORIES = [
  'group_vars',
] as const;

export const REQUIRED_PLAYBOOK_FILES = [
  'playbook.yml',
  'inventory.example',
  'group_vars/all.yml',
  'README.md',
] as const;

export interface PlaybookStructureOptions {
  playbookName: string;
  outputDir: string;
  dryRun?: boolean;
}

export interface PlaybookStructureResult {
  playbookDir: string;
  createdDirs: string[];
}

export async function createPlaybookStructure(
  options: PlaybookStructureOptions
): Promise<PlaybookStructureResult> {
  const { playbookName, outputDir, dryRun = false } = options;
  const playbookDir = join(outputDir, playbookName);
  const createdDirs: string[] = [];

  if (!dryRun) {
    await mkdir(playbookDir, { recursive: true });
  }
  createdDirs.push(playbookDir);

  for (const dir of PLAYBOOK_DIRECTORIES) {
    const dirPath = join(playbookDir, dir);
    if (!dryRun) {
      await mkdir(dirPath, { recursive: true });
    }
    createdDirs.push(dirPath);
  }

  return {
    playbookDir,
    createdDirs,
  };
}
```

### Idempotency Checker Path Filter

Current checker only validates `tasks/` paths. For playbooks, also validate `playbook.yml`:

```typescript
// In idempotency-checker.ts

function isTaskFile(path: string): boolean {
  const isYaml = path.endsWith('.yml') || path.endsWith('.yaml');
  const inTasks = path.includes('tasks/');
  const isPlaybook = path.endsWith('playbook.yml');
  return isYaml && (inTasks || isPlaybook);
}
```

**Note:** The existing checker parses arrays of tasks. Playbooks have plays containing tasks, so parsing logic needs adaptation:

```typescript
// Handle playbook structure: array of plays, each with tasks
if (Array.isArray(parsed)) {
  for (const item of parsed) {
    if (typeof item !== 'object' || item === null) continue;

    // Check if this is a play (has 'hosts' key) or a task
    if ('hosts' in item && 'tasks' in item) {
      // It's a play - check its tasks

          }
```

## Playbook Name Inference

Extend sanitize.ts with playbook-specific inference:

```typescript
export function inferPlaybookName(description: string): string {
  let text = description.toLowerCase();

  // Strip common action words
  const PLAYBOOK_ACTION_WORDS = [
    'deploy',
    'provision',
    'configure',
    'setup',
    'set up',
    'install',
    'create',
    'manage',
    'update',
    'upgrade',
  ] as const;

  for (const action of PLAYBOOK_ACTION_WORDS) {
    const actionRegex = new RegExp(`^${action}\\s+`, 'i');
    if (actionRegex.test(text)) {
      text = text.replace(actionRegex, '');
      break;
    }
  }

  // Remove filler words (same as role)
  const fillerRegex = new RegExp(`\\b(${FILLER_WORDS.join('|')})\\b`, 'gi');
  text = text.replace(fillerRegex, '');

  const words = text.split(/[\s,]+/).filter((w) => w.length > 0 && w.length <= 20);
  const meaningfulWords = words.slice(0, 3);

  if (meaningfulWords.length === 0) {
    return 'playbook';
  }

  return sanitizeRoleName(meaningfulWords.join('-')); // Reuse same sanitization
}
```

## Common Pitfalls

### Pitfall 1: Handlers Scope Confusion
**What goes wrong:** Handlers defined play-level but referenced across plays
**Why it happens:** Handlers are play-scoped, not playbook-scoped
**How to avoid:** System prompt explicitly states "handlers are per-play"
**Warning signs:** Handler not found errors when running playbook

### Pitfall 2: Inventory Group Mismatch
**What goes wrong:** Playbook `hosts:` patterns don't match inventory.example
**Why it happens:** AI generates different group names
**How to avoid:** Plan schema includes `inventory_groups`, generation prompt emphasizes matching
**Warning signs:** "No hosts matched" when running playbook

### Pitfall 3: become: Overuse
**What goes wrong:** Setting `become: true` at play level when only some tasks need it
**Why it happens:** Simpler to set once
**How to avoid:** System prompt says "become: on tasks that need it, not play-level"
**Warning signs:** Tasks run with unnecessary privilege escalation

### Pitfall 4: Missing Variable Validation
**What goes wrong:** Playbook fails mid-run due to undefined variables
**Why it happens:** No pre_tasks validation
**How to avoid:** System prompt mandates assert/fail in pre_tasks
**Warning signs:** Cryptic undefined variable errors

### Pitfall 5: Idempotency Checker False Negatives
**What goes wrong:** Checker doesn't find issues in playbooks
**Why it happens:** Checker only looks at `tasks/` path, not `playbook.yml`
**How to avoid:** Update path filter to include playbook files
**Warning signs:** FQCN/idempotency warnings not appearing
